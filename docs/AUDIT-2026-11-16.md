# Аудит надёжности, 16 ноября 2026

Listik — локальный редактор списков с зашифрованной синхронизацией нескольких устройств. Проверка сосредоточена на сохранении и восстановлении данных, сервере синхронизации и выпуске. Предполагается один процесс сервера, несколько устройств и постепенно растущий документ.

## Исправлено первым

1. **P1: файл снимка и его номер могли расходиться** (`server/index.js`, `putSnapshot`, обработчик GET snapshot).
   Новый файл перезаписывал `snapshot.bin` до сохранения `snapshotSeq`. Сбой записи метаданных и перезапуск оставляли новые байты со старым номером; номер входит в AES-GCM AAD, поэтому клиент не мог открыть снимок. GET также мог прочитать старые байты и затем отправить новый номер при конкурентном PUT.
   Исправление: отдельный файл каждой версии, атомарная публикация имени и номера через метаданные, чтение в очереди документа. Тесты: ошибка записи метаданных, перезапуск, совместимость со старым файлом, замена на том же номере, конкурентные GET/PUT.

## Следующие исправления

2. **P1: ошибочные PUT на новые ID неограниченно увеличивают кэш документов** (`server/index.js`, `handle`, `docFor`).
   `PUT /docs/<новый-id>/keyslot` с телом `{}` сначала создаёт объект в `docs`, затем отвечает 400. Удаление пропускается из-за `creating`, а `noteFailure` для этой ошибки не вызывается. Повторение запроса с новыми ID накапливает объекты без ограничения, даже при выключенном создании документов.
   Исправление: проверять тело до создания объекта и освобождать незавершённые записи с учётом конкурентных запросов. Иначе память процесса можно исчерпать неавторизованными запросами. Вывод по коду; нагрузочная атака на прод не проводилась.

3. **P2: неудачное создание документа публикует состояние только в памяти** (`server/index.js`, `Document.create`).
   `this.meta` присваивается до записи keyslot и метаданных. При отказе диска PUT возвращает 500, но последующие запросы считают документ существующим; после перезапуска он может исчезнуть, поскольку `meta.json` так и не появился.
   Исправление: записывать подготовленные метаданные и только после успеха публиковать их в памяти. Иначе ошибка диска оставляет частично созданный документ с противоречивыми ответами API. Вывод по последовательности записи; отдельный регрессионный тест пока не добавлен.

## Границы проверки

Проверки: 469 unit-тестов, проверка типов и production-сборка прошли. Новый регрессионный тест отдельно падает на исходном master и проходит с исправлением. Полный e2e-прогон: 307 прошли, 2 упали, 4 не запустились. Один сбой вызван устаревшим селектором меню в тестах синхронизации; селектор исправлен, все 5 сценариев синхронизации затем прошли (обмен двух браузеров, восстановление, офлайн, разрыв журнала, смена пароля).

Оставшийся e2e-сбой воспроизведён на исходном master: при размере окна 915×190 нижняя граница редактируемой строки 140.4375 px заходит под панель, начинающуюся на 137 px (`e2e/outline.spec.ts:2765`). Это отдельный дефект интерфейса; серверное исправление его не меняет. Полностью зелёным e2e-набор не является.

Прочитаны сервер, движок синхронизации, ключевые пути IndexedDB, часть подключения синхронизации и резервного копирования, тесты сервера и конфигурация CI. Полного построчного аудита UI, Electron и всех команд модели не было. Оставшиеся пункты не входят в исправление № 1.

Новый формат снимков требует подготовки файлов перед откатом на старый сервер — процедура описана в `server/DEPLOY.md`. Аварийное завершение до публикации может оставить неиспользуемый файл снимка; подтверждённый снимок остаётся целым.
